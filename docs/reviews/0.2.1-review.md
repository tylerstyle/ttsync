# Code Review: 0.2.1 — Deletions from TimeTree's change list

- **Reviewer:** Claude Code, standing in for the usual reviewer
- **Date:** 2026-11-17
- **Commits reviewed:** `7ba7a30..b083792` (`47cb8f4` debug probe, `25de3b7` change list, `b083792` docs)
- **Checked:** `./gradlew --no-daemon testDebugUnitTest`: 428 tests, all green (lint and assemble not re-run)

**Verdict: Not ready** (0 blockers, 1 should-fix, 3 nits)

The deletion path itself is correct and safe. A tombstone from the change list deletes exactly its
mapped, in-window copy, through the R1-verified gateway. An INCREMENTAL read can't prove absence,
and the FULL safety net is intact. One gap remains: the "change list unusable" fallback catches a
list that answers in an unexpected way, but not an endpoint that refuses to answer. A 403/404 there
pauses the calendar for good (SHOULD-FIX-1). That fix is a few lines plus a test. After it, the
release is ready; the nits can follow.

## Focus area verification

1. **Correctness of deletions:** no finding.
   - **Mode and request.**
     [`fetch`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L745-L764) decides
     FULL first. Otherwise it asks `changes(id, highWater − 2 min)`. A `null` answer turns the run
     FULL.
   - **No proof of absence.**
     [`ChangeFeed.read`](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/ChangeFeed.kt#L40-L69)
     always returns `complete = false`, and
     [`provesAbsence`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L781-L782)
     also needs `full`. So the change list can delete only through `Desired.Absent`.
   - **Mapping a tombstone.**
     [`mapEvents`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L830-L855) merges
     the stored and fetched events by uuid, so the tombstone replaces the stored live version. Every
     tombstone that isn't in `desired` becomes `Absent`, whatever its times.
   - **Diff.** The uuid is in
     [`affected`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L858-L865).
     [`plan`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L956-L962) deletes only
     `mappingFor(uuid)` (current target) with `endAt >= windowStart`.
   - **Snapshots.**
     [`commit`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1080-L1090) drops
     the snapshot of a non-override tombstone
     ([`isStorable`](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1204-L1205)).
     A FULL never keeps one either, because `storedToKeep` only keeps stored tombstones, which are
     override tombstones.
   - **Cases checked:**
     - a mapping in the window: one verified delete;
     - a mapping out of the window: untouched;
     - no mapping (the event was created and deleted between two runs): nothing;
     - a tombstone read again in the overlap after its copy is gone: no operation;
     - an undecodable entry: never in `affected`.
   - **High-water mark.** An INCREMENTAL run takes the maximum of the old mark and every fetched
     `changedAt`, tombstones included
     ([SyncEngine.kt:777-779](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L777-L779)),
     so the cursor moves past deletions. Malformed entries don't move it, so they are read again
     and stay skipped. A FULL sets the mark to the newest *live* change, which can be lower than the
     last INCREMENTAL's mark. The next INCREMENTAL then reads tombstones that were already applied
     again, which writes nothing.
     - One bounded edge: a FULL read of a very large calendar can take more than 2 min. If an event
       is deleted early in that read (its page already read) and another event is edited later in
       it, the deletion can fall below the next `since`. The next FULL (≤ 6 h) removes that copy.
   - **Series:**
     - Deleting one date is an edit of the series (EXDATE), so its copy gets an UPDATE.
     - Deleting the whole series sends one tombstone, which deletes the series' copy
       (`deletingASeriesInTimeTreeDeletesItsCopyWithTheNextRun`).
     - An override tombstone is stored, deletes its copy, and makes the engine compare the parent
       again (`parentOf`). For their storage, see NIT-2.
     - The device probe of 2026-11-17 didn't cover deleting a series that has moved occurrences, or
       deleting a moved occurrence.

2. **Safety:** no finding.
   - Deletes still come only from `plan`: `Absent` with an in-window mapping in the current target,
     or a complete FULL. The adoption scan's duplicates and leftovers are unchanged.
   - Paused calendars are never fetched
     ([SyncEngine.kt:637-640](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L637-L640)).
   - Skipped uuids are kept out of `affected` and out of the absence loop.
   - `anIncrementalRunNeverDeletesByAbsence` covers the change list.

3. **"Change list unusable" fallback:** gap in SHOULD-FIX-1.
   - **The four checks match the probe**
     ([ChangeFeed.kt:47-57](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/ChangeFeed.kt#L47-L57)).
     The server returns `updated_at >= since`, and "older than since" uses a strict `<`, so the
     inclusive `since` and the 2-min overlap can't raise it. Equal timestamps can't raise "not
     ordered" either. No false alarms on data shaped like the probe's.
   - **Malformed entries.** An entry enters the checks only through its own readable `updated_at`;
     one without it is skipped. So a malformed entry can trigger the fallback only if its own
     `updated_at` really is out of order. The worst case is a harmless FULL. This includes a
     tombstone without `updated_at`, which decodes with `deactivated_at`, about 30 ms earlier.
   - **`chunk == true` never seen:** reasonable.
     - INCREMENTAL reads cover at most 6 h of changes; a run after a longer pause is FULL. A second
       page needs a burst of more than one page of changes.
     - The read follows `since` only while it moves forward and the order holds. Anything else
       reads FULL.
     - The one thing it can't see is a server that drops entries at a page boundary (for example
       equal `updated_at` values split across pages, with `since` = newest + 1). The 6-hourly FULL
       bounds that.
   - **Not caught:** endpoint-level failures (SHOULD-FIX-1).
   - **A list that stays unusable** costs two reads per run (the change list, then FULL). That is
     acceptable, and each run logs it.

4. **Removal of the small-feed rule:** no code finding.
   - **What small calendars lose: the next run → the next FULL (≤ 6 h):**
     - a copy deleted, or stripped of its marker, in Google comes back at the next FULL
       ([DESIGN.md](../DESIGN.md) section 5, "Deleting a copy in Google", already says so);
     - a renamed label reaches the copies at the next FULL (section 4a already says so);
     - duplicates and filter leftovers are cleaned whenever the scan runs: on FULL, after a crash,
       with empty mappings, or for an unmapped write.
   - **Unaffected:**
     - adoption (`needsAdoption`,
       [SyncEngine.kt:662-665](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L662-L665);
       `e6WipedMappingsGetAdopted`);
     - filter changes (`filterHash` forces FULL);
     - an unknown label id (the labels are fetched again);
     - `filterImpact` (snapshots stay merged).
   - `unmanagedMarked` is 0 in runs without a scan, but it is only logged, not shown.

5. **Upgrade 0.2.0 → 0.2.1:** no trap.
   - The cursor is reused. `EventMapper.VERSION` is unchanged, so no FULL is forced. 0.2.0 cursors
     have `lastFullPages`.
   - The first 0.2.1 run reads the change list from the 0.2.0 mark minus 2 min, so deletions after
     that arrive at once.
   - A deletion that a 0.2.0 INCREMENTAL run (large calendar) had already passed waits for the next
     FULL, ≤ 6 h after the last 0.2.0 FULL. That is the bound 0.2.0 already had.
   - An empty calendar's mark of 0: see NIT-1.

6. **Debug probe in main code:** acceptable.
   - Only `DebugReceiver` calls `probeEvents`. That receiver is in the debug source set and guarded
     by `DUMP`.
   - The release build minifies ([app/build.gradle.kts:76](../../app/build.gradle.kts#L76)) and no
     keep rule mentions the probe, so R8 can drop it, `ProbeList` and `ProbePage`.
   - It doesn't take the engine lock and switches the dump folder. That is documented ("not during
     a sync") and matters for debug dumps only.

7. **Tests and docs:**
   - **What the tests cover:**
     - Client C9 tests: forward paging, tombstones, an empty answer, the four distrust rules, 404 →
       `AccessLost`.
     - Engine tests: an edit, a new event and a tombstone in one INCREMENTAL run; one request
       without changes; a deleted series; the fallback; a small calendar running INCREMENTAL; the
       6-hourly FULL catching a purge; no deletes by absence; a skipped uuid through the change
       list.
   - **Gaps:**
     - no engine test for a 403/404 or an undecodable page on the change list (SHOULD-FIX-1);
     - no test for a deleted moved occurrence arriving through the change list: its copy goes, the
       tombstone is stored, the parent is compared again, and the next FULL keeps the tombstone and
       deletes nothing else;
     - the empty-calendar test sends `since=-120000` to a fake that accepts anything (NIT-1).
   - **Device test still to do.** [DEVICE-TESTS.md](../DEVICE-TESTS.md) has no 0.2.1 entry. The
     device probe only read the lists; no 0.2.1 sync over the change list is recorded on a device
     yet. Before the release, run one on the phone and check that each copy goes with "Sync now":
     - delete an event;
     - delete one date of a series;
     - delete a moved occurrence;
     - delete a whole series.
   - **Docs.** [DESIGN.md](../DESIGN.md) sections 3 and 5 and the [README](../../README.md) describe
     the new behaviour correctly, apart from the points in NIT-3. Several other sections still
     describe the small-feed rule (NIT-3).

## Findings

### SHOULD-FIX-1: A 403/404 from the change list pauses the calendar instead of falling back to FULL

[OkHttpTimeTreeClient.kt:216-219](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/OkHttpTimeTreeClient.kt#L216-L219),
[SyncEngine.kt:752](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L752),
[SyncEngine.kt:793-795](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L793-L795),
[SyncWorker.kt:125-129](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncWorker.kt#L125-L129)

The fallback covers how the list behaves (order, cursor, page count). It doesn't cover the endpoint
itself:

- **403 or 404 on `/calendar/{id}/events`** becomes `TtError.AccessLost` (`Endpoint.Changes` carries
  the calendar id). `timeTree {}` rethrows it, and `fetch` catches it and **pauses** the calendar. The
  worker shows the "No access to a TimeTree calendar" notification. If that was the only calendar,
  it cancels the periodic work.
- **The pause is sticky.** Paused calendars are never fetched again, and the only way out in the UI
  is "Remove copies" or deselecting, which deletes the copies. After a re-selection, the next
  INCREMENTAL run pauses it again.
- **Any other 4xx, or a page that doesn't decode,** is `ApiChanged`. It fails the whole run, for
  every calendar, on every INCREMENTAL run.

Scenario: TimeTree retires or restricts `/calendar/{id}/events`, an unofficial endpoint verified on
one calendar of one account (the device probe of 2026-11-17). `/events/sync` keeps working.

- The same run has just listed the calendar as active in `/calendars`, and a FULL read would succeed.
- Yet every 0.2.1 user gets each calendar paused at its next INCREMENTAL run, with an access-lost
  notification, and their sync stops.
- 0.2.0 would have kept syncing.

`c9_changesFailLikeEvents` asserts the `AccessLost`, so the behaviour is deliberate. But for this
endpoint, a refusal says nothing about access that `/events/sync` can't say better.

Fix: in `OkHttpTimeTreeClient.changes`, or around `feed.read`:

- Treat `AccessLost` and `ApiChanged` as "unusable": log the HTTP status and return `null`.
- Keep `Transient`, `RateLimited` and the auth errors as they are.
- If access really is lost, the FULL read gets the same 403/404 from `/events/sync` and pauses as
  before, at the cost of one extra request.
- Update the KDoc of `TimeTreeClient.changes` and the C9 test.
- Add an engine test: a 404 on `changes` gives a FULL run and no pause.

### NIT-1: An empty calendar sends a negative `since`

[SyncEngine.kt:751](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L751),
[SyncEngine.kt:778](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L778)

Scenario:

1. A FULL of a selected calendar with no live events stores `highWater = 0`
   (`anEmptyCalendarStoresHighWaterZero`). Examples: a new shared calendar, or one where every
   event was deleted.
2. Every later INCREMENTAL run then requests `/calendar/{id}/events?since=-120000`. Each FULL sets
   the mark back to 0, so this repeats while the calendar stays empty.

The probe tested `since=0` and positive values only. Two possible answers:

- **The server treats the value like 0:** fine (the whole list, tombstones included, with no effect).
- **It rejects the value with a 4xx:** that is `ApiChanged`, and every such run fails for all
  calendars.

Fix: `(highWater − overlap).coerceAtLeast(0)`. SHOULD-FIX-1 would also soften the rejection case to
one extra FULL per run.

### NIT-2: Override tombstones are now stored and never removed

[SyncEngine.kt:486-490](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L486-L490),
[SyncEngine.kt:850-854](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L850-L854),
[SyncEngine.kt:1204-1205](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1204-L1205)

The code that stores override tombstones is from 0.2.0, but `/events/sync` never delivered any, so
it is new in practice. Scenario:

1. A moved occurrence of a series is deleted. Its tombstone, with `recurring_uuid` set, arrives
   through the change list and is stored (`isStorable`).
2. No path ever drops it:
   - every FULL keeps it (`storedToKeep` keeps every stored deactivated snapshot that the fetch
     lacks);
   - INCREMENTAL drops only fetched, non-storable events;
   - it stays even after it leaves the window, or after its series is deleted (the series' own
     tombstone is dropped, its override tombstones stay).
3. Every run maps it to `Absent`, and every FULL puts it into `affected` (no operation).

The cost is one row per deleted moved occurrence, forever. That is small, but it is unbounded.
Optional fix: drop an override tombstone once its parent is gone or its end is before the window.
