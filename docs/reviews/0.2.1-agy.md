## Focus Area Verification

1. **Correctness of deletions (`ChangeFeed.kt`, `FeedEntries.kt`, `SyncEngine.kt`):**
   - **Forward change list (`ChangeFeed`):** [ChangeFeed.kt](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/ChangeFeed.kt#L37-L66) pages forward through `GET /calendar/{id}/events?since=<cursor>` while `chunk == true`, deduplicating entries per `uuid` via [FeedEntries.kt](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/FeedEntries.kt#L37-L73) by newest `changedAt = max(updated_at, deactivated_at)`.
   - **High-water mark:** On the device probe of 2026-11-17, a deletion sets `deactivated_at` and bumps `updated_at` (~30 ms after `deactivated_at`). `EventsResult.highWater` takes `maxOfOrNull { it.event.changedAt }`, and [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L778-L779) updates `work.highWater = maxOf(cursor.highWater ?: 0L, result.highWater ?: Long.MIN_VALUE)`, advancing the high-water mark to the newest edit or tombstone without ever storing the server's `since`.
   - **Mapping and verified delete:** In [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L839-L855), an `INCREMENTAL` run merges stored snapshots with `fetchedEvents` (`work.storedEvents + fetchedEvents.associateBy { it.uuid }`), so a fetched tombstone replaces the stored live snapshot in `events`. Both `DefaultEventMapper` and the fallback in `mapEvents` map every valid-uuid tombstone to `Desired.Absent`. Because `changed = work.fetchedUuids` is in `affected(work)`, [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L956-L961) plans `CalendarOp.Delete(mapping.eventId, uuid)` (`Kind.DELETE`) if and only if `mappingFor(uuid)` exists in the current target and `mapping.endAt >= windowStart`.
   - **Snapshot cleanup (`commit`):** In [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1080-L1090) and `#L1204-L1205`, `TtEvent.isStorable()` is `if (isDeactivated) isOverride else !isBirthday && !isMemo`. In an `INCREMENTAL` run (`!work.provesAbsence`), non-override tombstones go into `drop` (`db.snapshots.delete(drop)` removes the stale live snapshot from SQLite), while override tombstones (`recurring_uuid` / `parent_id` set) go into `keep` (`db.snapshots.upsert(keep)`) so `OverrideResolver` retains them on later runs.
   - **Recurring series and single occurrences:** Deleting one unmodified occurrence of a series adds an `EXDATE` to the series parent and bumps the parent's `updated_at` (confirmed by the device probe of 2026-11-17), so the parent arrives in `changes` as an edited live series and its copy is updated in place. Deleting an entire series produces a tombstone for the series parent, which deletes the series copy on the next `INCREMENTAL` run (`SyncEngineTest.deletingASeriesInTimeTreeDeletesItsCopyWithTheNextRun`).

2. **Safety (`ChangeFeed.kt`, `SyncEngine.kt`):**
   - **No absence deletes in `INCREMENTAL`:** `ChangeFeed.read` always sets `complete = false` ([ChangeFeed.kt](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/ChangeFeed.kt#L65)), and [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L781-L782) requires `full && result.complete && result.skippedMalformed <= result.skippedUuids.size` for `work.provesAbsence`. An `INCREMENTAL` run can never delete by absence (`SyncEngineTest.anIncrementalRunNeverDeletesByAbsence`).
   - **Unknown state, paused calendars, and window boundary:** Malformed entries in `ChangeFeed` are tracked in `skippedUuids` by `FeedEntries` (with `version = Long.MAX_VALUE` when `updated_at` is missing) and excluded from `activeWrites`, `activeFiltered`, and `affected`. Paused calendars are skipped before `fetch`. Out-of-window mappings (`mapping.endAt < windowStart`) and unmapped tombstones (e.g., 5-day-old tombstones re-read inside the 2-minute overlap) are never deleted. Every delete goes through `CalendarGateway`'s R1 marker verification and R2 `_ID` precondition.

3. **"Change list unusable" fallback (`ChangeFeed.kt`, `SyncEngine.kt`):**
   - **Anomaly checks vs. real data:** [ChangeFeed.kt](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/ChangeFeed.kt#L46-L58) verifies four invariants:
     1. `pages < maxPages` (500);
     2. `updatedAt >= cursor` (matches the inclusive `updated_at >= since` boundary confirmed on the device probe, including with the 2-minute overlap on page 1 and `page.since = newest + 1` on subsequent pages);
     3. `previous == null || updatedAt >= previous` (allows equal `updated_at` timestamps while rejecting descending/out-of-order entries; concurrent edits during forward paging move entries to higher `updated_at` at the tail of the list, never earlier);
     4. when `page.chunk == true`, `page.since > cursor`.
   - **Malformed entries:** In `val updatedAt = entries.add(json) ?: continue`, a malformed entry without a readable `updated_at` is recorded in `skippedUuids` / `skippedWithoutUuid` and skipped by the ordering check without triggering a false alarm. If a malformed entry carries a bogus `updated_at < cursor` or `< previous`, `ChangeFeed` returns `null` and `SyncEngine.fetch` falls back to `FULL` (`client.events(work.id)`), which is safe.
   - **Unseen `chunk == true`:** Because the test calendar had 17 entries (one page), guarding `page.chunk == true` with `page.since > cursor`, `updatedAt >= cursor`, `updatedAt >= previous`, and `maxPages` is the right defence: if a multi-page `/events` response ever paged backwards or stalled, `ChangeFeed` immediately returns `null` and the engine runs `FULL` via `/events/sync` for that calendar.

4. **Removal of the small-feed rule (`SMALL_FEED_PAGES`):**
   - **Deletions:** Now handled on every `INCREMENTAL` run via tombstones in `ChangeFeed`, with the 6-hourly `FULL` as a safety net for tombstones dropped while a phone was off for days.
   - **Adoption after lost mappings:** `affected()` in [SyncEngine.kt](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L863) includes `unmapped` (`Desired.Write` uuids from `storedEvents + fetchedEvents` that have no mapping), and `needsAdoption` triggers `scan(withDuplicates = true)` even on an `INCREMENTAL` run (`SyncEngineTest.e6WipedMappingsGetAdopted`).
   - **Filter changes:** Force `FULL` via `cursor.filterHash != filterHash` and `UserActions.saveSources`, independent of feed size.
   - **Copies deleted in Google & label renames:** Repaired / refreshed on the 6-hourly `FULL` (or "Full resync"), matching how >3-page calendars already behaved in 0.2.0.

5. **Upgrade 0.2.0 → 0.2.1:**
   - Reusing `cursor.highWater` without a schema bump is sound: live events in `/events` and `/events/sync` are byte-for-byte identical with the same `updated_at` values. Any deletion that happened after 0.2.0's last `highWater` is picked up on the first 0.2.1 `INCREMENTAL` run; any deletion that occurred on a >3-page calendar in 0.2.0 *before* a subsequent 0.2.0 live edit advanced `highWater` past the deletion is caught by the next 6-hourly `FULL` run (no worse than 0.2.0).

6. **Debug probe in main code (`OkHttpTimeTreeClient.probeEvents`):**
   - Keeping `probeEvents`, `ProbeList`, and `ProbePage` on `OkHttpTimeTreeClient` (not on the `TimeTreeClient` interface) is clean: it lets unit tests (`OkHttpTimeTreeClientTest`) exercise `probeEvents` against MockWebServer, `DebugReceiver` exists only in `src/debug`, `rawSink` is a no-op in release, and R8 strips the unused methods and classes from the release APK.

7. **Tests and documentation:**
   - Unit tests in [OkHttpTimeTreeClientTest.kt](../../app/src/test/kotlin/de/tergelius/ttsync/timetree/OkHttpTimeTreeClientTest.kt#L175-L331) and [SyncEngineTest.kt](../../app/src/test/kotlin/de/tergelius/ttsync/sync/SyncEngineTest.kt#L1005-L318) cover multi-page forward paging, tombstones, series deletion, empty change lists, all four distrust fallback conditions, `probeEvents`, and the 6-hourly `FULL` safety net.
   - Two minor stale doc comments from the old small-calendar rule are noted as NIT-1 below.

- **Locations:**

- **Scenario:**
  Sections 3, 5, 10, and 14 of `DESIGN.md` and `StoreModels.kt:79` were updated for 0.2.1, but three earlier places still state the 0.2.0 rule:
  1. `docs/DESIGN.md:31`: *"Sync every hour. Reconcile fully on every run for a small calendar, otherwise at least every 6 h (section 5)."*
  2. `docs/DESIGN.md:529-531`: *"The adaptive FULL (section 5) keeps that promise: it never adds runs, and a run that reads a small calendar completely costs a few requests, the same order as an incremental one."*
  3. `TimeTreeClient.kt:113-115` (`EventsResult.feedPages` KDoc): *"The engine keeps it to choose between FULL and INCREMENTAL runs (`SyncCursor.lastFullPages`)."*
- **Fix:**
  Update those three comments to match section 5 and `StoreModels.kt` (every calendar runs `INCREMENTAL` between the 6-hourly `FULL`s; `feedPages` is kept for logging).
