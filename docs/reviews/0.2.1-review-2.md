Step 6a is safe. It deletes a row again only when four things hold:

- the row is in the current target, of an active calendar;
- it still carries the marker of the uuid the app deleted;
- that uuid isn't wanted by any active calendar;

`storedToKeep` rule are correct. The fix round closed the first review's findings, except one case:
a 401 from the change list still goes down the sign-in path (SHOULD-FIX-1). That fix is about one

## Findings

### SHOULD-FIX-1: A 401 from the change list blocks automatic sign-in instead of falling back to FULL

[OkHttpTimeTreeClient.kt:206](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/OkHttpTimeTreeClient.kt#L206),
[:218-226](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/OkHttpTimeTreeClient.kt#L218-L226),
[:130-138](../../app/src/main/kotlin/de/tergelius/ttsync/timetree/OkHttpTimeTreeClient.kt#L130-L138),
[StoredSessionStore.kt:37-39](../../app/src/main/kotlin/de/tergelius/ttsync/settings/StoredSessionStore.kt#L37-L39)

`changes()` now turns `AccessLost` and `ApiChanged` into "read completely". A 401 never gets that
far: `dataExchange` treats a 401 on any endpoint as an auth failure.

Scenario: TimeTree starts answering 401 on `/calendar/{id}/events` for the web session (an endpoint
restricted to other clients), while `/calendars` and `/events/sync` keep working.

1. The run's `/calendars` succeeds with the stored session.
2. The change list answers 401. The client signs in again, which succeeds (`onAutoLoginSucceeded`),
   and repeats the request.
3. The second 401 calls `onAutoLoginRejected()`, which starts the 6-hour block of automatic sign-ins,
   and throws `AuthRejected`. That fails the whole run with `AUTH_REJECTED` (`userMustAct`), which
   notifies at once: "TimeTree rejected the stored sign-in … Sign in again".
4. The next runs:
   - while the block lasts, the 401 meets a refused automatic sign-in and fails as `NOT_SIGNED_IN`;
   - a second rejection in a row stops automatic sign-ins until the user signs in again;
   - after the user signs in, the next INCREMENTAL run starts the cycle again.
5. The password was never wrong, and a FULL read would have worked.

My first review said to keep the auth errors as they are; for this case that was wrong.

Fix:

- Don't count a 401 on `Endpoint.Changes` as an auth failure, so it falls through to `ApiChanged`
  and `changes()` returns `null`.
- The same run's `/calendars` has just accepted the session. If the session really expired, the FULL
  read's own requests sign in again as usual.
- Add a C9 test: 401 → `null`, with no `onAutoLoginRejected`.

### NIT-1: A delete done again renews `deleted_at`, so the 30-day limit never ends a restore loop

[SyncEngine.kt:1116-1120](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1116-L1120),
[PendingDeletes.upsert](../../app/src/main/kotlin/de/tergelius/ttsync/store/SqlSyncDatabase.kt#L142-L152)

A successful `REDELETE` records a new `PendingDelete(…, nowMillis())`, and `INSERT OR REPLACE`
overwrites the first `deleted_at`.

Scenario: Google restores the same row after every delete. D1's trigger is unknown; it came "right
after a feed sync", and each run with a delete asks Google to sync.

- Every run deletes the row again, reports "Deleted 1" and asks Google to sync.
- The 30-day limit never applies.
- The contract "a run after an unchanged TimeTree writes nothing" stops holding.

Fix: keep the first `deleted_at` when a `REDELETE` succeeds, or count the attempts. After the limit,
log it, or show it on Status, rather than deleting forever.

### NIT-2: Deletes outside the diff aren't watched, so a restore after them leaves a copy for good

- [SyncEngine.kt:188-215](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L188-L215)
  (`deselect`)
- [:305-320](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L305-L320)
  (`deleteVerified`)
- [:1132-1135](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L1132-L1135)
  (a refused `DELETE`)

Section 5, step 6a, says the removal actions aren't watched, but not what follows. Two cases:

- **Deselect.** The user deselects a calendar, and its copies are deleted (`deleted = 1`). If Google
  restores some, as in D1:
  - the calendar is no longer selected, so no run ever looks at those rows;
  - they stay in Google as unmanaged copies that never change again;
  - the only way to remove them is "Remove all copies", which removes everything and stops syncing.

  A target change (old calendar) and removal at sign-out behave the same.
- **A delete that finds its row already `deleted = 1`.** The user deleted the copy in Google just
  before, or the app crashed between the provider delete and the record. The delete comes back as
  `Rejected(DELETED)`: the mapping is dropped and nothing is watched. If Google then restores the
  row, the copy of a deleted TimeTree event stays, unmanaged.

Fix:

- Record a `PendingDelete` for `Rejected(DELETED)` too (a few lines).
- For deselect, either:
  - keep the entries of the deselected calendars, and let 6a delete their restored rows again (the
    user confirmed the removal) unless the uuid is wanted or mapped; or
  - say in DESIGN.md and the README that such a restore stays until "Remove all copies".

### NIT-3: Step 6a's delete sits outside two "leave alone" rules and outside the safety contract

[SyncEngine.kt:59-63](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L59-L63),
[:670](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L670),
[:923-931](../../app/src/main/kotlin/de/tergelius/ttsync/sync/SyncEngine.kt#L923-L931)

**The contract.** The contract lists what a sync may delete: the diff's in-window mappings,
duplicates and leftovers. The unmapped rows that step 6a deletes again aren't there.

**Two rules 6a doesn't follow:**

- **Skipped uuids.** `activeWrites` leaves skipped (unreadable) uuids out, so 6a deletes a restored
  row of an event whose state is unknown in this run. Everywhere else such a row is left alone.

  Scenario:
  1. A filter excludes an event, and its copy is deleted and watched.
  2. Google restores the copy.
  3. The user widens the filter. In that FULL run the event doesn't decode, so it is skipped.
  4. 6a deletes the restored row again.
  5. When the event decodes again, a new copy is inserted.
- **The window.** An entry stores no `end_at`, so a restored row is deleted again even after its
  event has left the window. Step 5 says out-of-window copies are never touched. This matters only
  for a live event that a filter excluded and that is wanted again once out of the window.

Both cases need D1 to happen. Neither loses data for good.

Fix:

- Keep watching, but don't delete again, entries whose uuid is in an active calendar's
  `skippedUuids`.
- Either store `end_at` in `pending_delete`, or state in the contract and in step 6a that a delete
  done again ignores the window.
